# История обращений клиента

## Что работает в v1

- Команда `php api/leads/cli/leads.php customer-history <lead UUID>` запускается только на сервере.
- Она берёт телефон и e-mail исходной заявки, нормализует их и сравнивает другие заявки по domain-separated HMAC. Исходные контакты не выводятся и отдельная копия контактов или HMAC в базе не создаётся.
- Поиск ограничен исходной заявкой и 4 999 последними сохранёнными заявками. Результат содержит не более 50 последних совпавших заявок в хронологическом порядке. В JSON явно указано, если сканирование или выдача были усечены.
- В результат входят только безопасные рабочие поля: ID и время заявки, форма, путь страницы, сумма, номер КП и маршрут страниц текущей вкладки. ФИО, телефон, e-mail, компания и содержимое свободных полей не выдаются.
- Браузер хранит в `sessionStorage` под ключом `egoe_lead_journey_v1` не более 20 уникальных страниц текущей вкладки и текущего дня: путь без query/hash, заголовок и время. Этот маршрут уходит на сервер только вместе с заявкой после согласия и сохраняется в уже существующем `payload_json`.

Формат SQLite остаётся v2. Это намеренно: переход к индексированной таблице связей требует отдельного двухэтапного релиза, при котором предыдущая версия сначала учится безопасно читать новую схему. Текущий объём и срок хранения позволяют выполнять ограниченный read-only поиск без рискованной миграции production-базы.

## Telegram-кнопка

Серверный callback-обработчик «История клиента» ↔ «Назад к заявке» реализован в
`api/telegram/`. Он использует ту же логику `CustomerHistory::forLead(...)`, редактирует
то же Telegram-сообщение и не хранит отдельную копию контактов.

Первичное сообщение также отправляет непосредственно российский сервер через существующий
SQLite outbox; Google Apps Script не используется. До production-активации оба направления
остаются fail-closed. Нужны токен бота, ID группы и Telegram user ID разрешённых
сотрудников. Полный порядок и приватная конфигурация описаны в `ops/telegram/README.md`.
