# Рабочий процесс

## Одна задача — одна ветка

```bash
git fetch origin
git worktree add ../stroibad-2-<task> -b agent/<task> origin/main
cd ../stroibad-2-<task>
npm ci
npm run check
```

Если в существующем worktree есть чужие изменения, его не очищают и не «чинят». Для новой задачи создают новый worktree.

## Локально или в Codex Cloud

Короткую диагностику и визуальные правки удобно выполнять локально. Долгие независимые пакеты можно запускать в Codex Cloud: облачная задача получает отдельный контейнер и GitHub checkout, поэтому не занимает рабочую машину и не зависит от состояния локального worktree.

Для репозитория используется один cloud environment:

- repository: `olmazen/stroibad-2`;
- setup: `npm ci`;
- проверка результата: `npm run check`;
- задача стартует от нужной GitHub-ветки, для зависимого этапа — от ветки нижнего stacked PR;
- production-секреты в environment не добавляются, потому что cloud-задачи готовят PR, а не публикуют production.

Cloud не видит незакоммиченные локальные файлы. Перед передачей задачи изменения нужно осмысленно закоммитить и отправить в отдельную ветку. Итог всё равно принимается только после просмотра diff и зелёного CI.

Зависимую работу можно начать до merge предыдущего этапа, но только отдельной веткой поверх него и stacked PR с предыдущей веткой в качестве base. После merge нижнего PR base следующего меняют на `main`.

## Границы задач

Рекомендуемое деление:

- инфраструктура/релиз;
- общие шаблоны и навигация;
- каталог и товарные данные;
- конкретная категория/контент;
- общий JavaScript или формы;
- дизайн конкретного экрана.

Массовую миграцию сначала запускают в чистой ветке, затем считают затронутые файлы и просматривают репрезентативные страницы. Нельзя смешивать её с несвязанными ручными правками.

Общий header/navigation/footer меняют только в `src/shared/site-shell.json` или `tools/site-shell.mjs`. После правки выполняют `npm run sync:shell`; HTML между shell-маркерами вручную не редактируют.

Товары и цены меняют только в `src/data/products.json`, затем выполняют `npm run sync:data`. Производные `assets/products.json`, `assets/catalog.json` и `assets/data/prices.json` вручную не правят.

Новый верхнеуровневый блок в `assets/js/site.js` запускают только через `EGOE_RUNTIME.run('стабильное-имя', fn)` или `value()` с явным fallback. Имя одновременно добавляют в `config/site-contract.json`; незаписанный IIFE и расхождение списка отклонит `npm run check:runtime`. Для внешнего runtime нельзя убирать timeout или конечное fallback-состояние без отдельного изменения контракта и теста.

После изменения общего `style.css`, `site.js`, `leads.js`, `kp.js`, `ad3d.js` или `fw3d.js` выполняют `npm run sync:runtime-assets`. Версии в HTML — content-hash и вручную не назначаются; `npm run build` отклонит 303 стандартные страницы и `/kp/` со старым query-параметром или без отдельного lead-модуля.

Формы меняют через `assets/js/leads.js` и контракт `leadDelivery`, а не копированием обработчика в страницы. `npm run check:leads` использует поддельный транспорт и не отправляет реальных заявок. Проверять живой endpoint реальной заявкой можно только как отдельный согласованный smoke-тест с известным получателем и последующим подтверждением доставки.

## Definition of done

Задача завершена, когда:

1. изменена только заявленная область;
2. `npm run check` проходит;
3. `dist/` не содержит служебных файлов;
4. `git diff --check` проходит;
5. для UI проверены desktop/mobile состояния затронутых страниц;
6. для массовых изменений указаны количества до/после;
7. в отчёте явно сказано, создавался ли preview и затрагивался ли production.

## Передача между сессиями

Ориентироваться нужно не на память чата, а на репозиторий. В конце незавершённой задачи оставить в описании PR или в `docs/tasks/`:

- цель и границы;
- branch/worktree и исходный SHA;
- что уже сделано;
- что проверено и какими командами;
- незакрытые вопросы;
- следующий безопасный шаг.

Пароли, персональные данные и временные ссылки туда не записываются.
