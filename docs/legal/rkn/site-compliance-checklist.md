# Чек-лист подготовки сайта к требованиям Роскомнадзора

Дата проверки: 23.08.2026. Объект: `www.egoe-life.ru`. Статус: **публичные документы готовы только с отключённым онлайн-сбором; работающие формы не допущены**.

Этот чек-лист разделяет подготовленные тексты и фактическое соблюдение. Наличие HTML-страницы или шаблона не доказывает выполнение организационной обязанности.

## Подтверждённые факты целевой архитектуры

- [x] текущий online collection gate закрыт: формы не должны создавать новые записи заявок или доказательств согласия до юридического и серверного approval;
- [x] заявка сначала должна записываться PHP-обработчиком в SQLite на хостинге REG.RU в РФ;
- [x] весь Google Apps Script/Telegram relay в релизе имеет `enabled=false`; полная заявка остаётся только в российской SQLite;
- [x] dormant `signal` реализован как два постоянных поля: `_subject = «Новая заявка на сайте EGOE»` и `Сообщение = «Заявка сохранена в российской базе»`; клиентских значений нет, но режим остаётся `OFF` до ст. 12 из-за возможной корреляции по transport timestamp;
- [x] dormant `technical` имеет закрытый payload: `_subject`, `leadId`, `formId`, `page.path`, `createdAt`; поля формы, IP/HMAC IP, user-agent и согласие не включены;

- [x] каждый relay-режим требует `enabled=true`, `cross_border_confirmed=true` и соответствующий `allow_signal` / `allow_technical` / `allow_full`; production release дополнительно отклоняет любое `relayEnabled=true`;
- [x] consent evidence schema v2 хранит 1095 дней только `lead_id`, `payload_hash`, `form_id`, `page_path`, версию/время/URL согласия и время приёма сервером, без полей формы, IP/HMAC IP и user-agent;
- [x] Яндекс Карты загружаются браузером автоматически с `loading="lazy"`, а не после клика;
- [x] оформлена [оценка баланса законного интереса для Яндекс Карт](./yandex-maps-balance-assessment.md); её организационное утверждение и сведения провайдера остаются открытыми ниже;

- [x] в реестре Роскомнадзора найдена запись Оператора № `64-22-007585`; наличие записи зафиксировано, но её охват новой архитектуры не подтверждён.

## Техническая приёмка объединённой ветки

Эти пункты нельзя отметить по одному legal-worktree: их нужно проверить после объединения backend, forms, shell и deployment.

- [ ] все формы отправляют данные только в собственный same-origin PHP endpoint;
- [ ] до approval каждая форма изначально заблокирована, same-origin status сообщает `{"enabled":false}`, POST возвращает отказ без записи в SQLite, а включение невозможно без защищённого серверного маркера;
- [ ] успешный ответ пользователю возвращается только после валидной и устойчивой записи заявки и согласия в SQLite;
- [ ] endpoint валидирует метод, размер, типы, телефон/e-mail, обязательность согласия и ограничивает злоупотребления;
- [ ] `leadId` идемпотентен: повтор запроса не создаёт дубликаты;
- [ ] SQLite, резервные копии, outbox и журналы недоступны из web-root;
- [ ] токены Google/Telegram, пароли и пути к базе отсутствуют в Git, HTML, JS и пользовательских ответах;
- [ ] тест подтверждает, что при `enabled=false` отсутствуют сетевые вызовы, outbox-задания и сообщения Google Apps Script/Telegram;
- [ ] для dormant `signal` тело байт-в-байт совпадает с двумя константами из кода; query, headers, body и прикладные журналы не содержат идентификаторов, страницы, времени события, IP, полей формы и сохраняемого ключа корреляции; отдельно оценена связь transport timestamp с `created_at`;
- [ ] приложение сохраняет в SQLite только keyed HMAC IP, без исходного IP и user-agent; отдельного прикладного access log нет; HMAC-секрет находится вне Git/БД, доступ ограничен, правило ротации и срок хранения утверждены;
- [x] access log хостинга проверен: raw IP, timestamp, method/path, status/bytes, referrer и user-agent; 10 gzip-ротаций, фактически около 10 дней, в публичных документах установлен максимальный срок 30 дней;
- [ ] для реализованного dormant `technical` тест подтверждает точный allowlist `_subject`, `leadId`, `formId`, `page.path`, `createdAt` и отсутствие полей формы, IP/HMAC IP, user-agent и согласия; аналогичные allowlist- и негативные тесты есть для `signal` и `full`;
- [ ] `signal`, `technical` и `full` по умолчанию выключены; активация невозможна без `cross_border_confirmed` и соответствующего mode-specific `allow_*`, не управляется клиентским параметром, а production release отклоняет `relayEnabled=true`;
- [ ] у outbox есть TTL, retry/backoff, лимит попыток, идемпотентность и очистка без записи полного payload в журнал;
- [ ] отдельный незаполненный чекбокс блокирует отправку каждой формы;
- [ ] consent evidence schema v2 хранит ровно `lead_id`, `payload_hash`, `form_id`, `page_path`, версию согласия, `acceptedAt`, URL документа и `receivedAt` в течение 1095 дней; полей формы, IP/HMAC IP и user-agent в evidence нет;
- [ ] версия согласия в frontend, backend и публичном документе совпадает;
- [ ] возле каждой формы есть прямые ссылки на `/consent/` и `/privacy/`;
- [ ] ссылки на privacy/consent/cookies доступны из общего подвала всех публичных страниц;
- [ ] баннер технического/функционального хранилища не заявляет, что продолжение просмотра равно согласию и не называет все функциональные ключи строго необходимыми;
- [ ] карта Яндекса и её автоматическая загрузка раскрыты до/рядом с картой либо понятны из доступной политики;
- [ ] на production включены HTTPS, безопасные заголовки, запрет directory listing, ограничения PHP и защита служебных файлов;

## Отдельный gate Google Apps Script → Telegram

В текущем релизе общий relay имеет `enabled=false`; dormant-режимы `signal`, `technical` и `full` недоступны, а полная заявка остаётся только в SQLite в РФ. Один `signal`-вызов сразу после каждой записи всё равно создал бы transport timestamp у Google/Telegram, который может сопоставляться с `created_at` в SQLite. Поэтому постоянное тело не освобождает будущий `signal` от обязательного gate ст. 12.

Технический режим реализован в dormant-коде с точным payload `_subject`, `leadId`, `formId`, `page.path`, `createdAt`. Эти значения относятся к конкретной заявке, поэтому relay рассматривается как потенциальная трансграничная передача персональных данных. Режим остаётся `OFF`, пока не закрыт обязательный пакет ст. 12; одного значения `enabled=true` недостаточно — сервер также требует `cross_border_confirmed=true` и `allow_technical=true`, а production release отклоняет любой включённый relay.

Для технического режима нужны:

- [ ] точные иностранные получатели, юридические лица, адреса и государства;
- [ ] сведения по ч. 5 ст. 12, датированная оценка и отдельное уведомление до начала передачи;
- [ ] истечение применимого срока ожидания для государств вне перечня адекватной защиты и отсутствие запрета/ограничения Роскомнадзора;
- [ ] утверждённые TTL, доступы и проверяемое удаление сообщений;
- [ ] allowlist- и негативные тесты точного payload; серверный допуск `cross_border_confirmed + allow_technical`, недоступный из клиента.

Full mode запрещён до одновременного выполнения всех пунктов:

- [ ] требования для технического режима выше выполнены;
- [ ] опубликованы обновлённые Политика и отдельное согласие;
- [ ] получено новое согласие пользователей, если оно является основанием передачи;
- [ ] установлены TTL и проверяемое удаление сообщений;
- [ ] проведён технический тест allowlist full mode и отдельный approval владельца.

## Решение по рекламному согласию

Публичная страница рекламного согласия сейчас не нужна. Статья 18 38-ФЗ требует предварительное доказуемое согласие для рекламы по сетям электросвязи, но сайт не заявляет рассылку. Текущий шаблон остаётся внутренним и не добавляется в формы.

## Условия допуска

Публичные документы можно публиковать только вместе с закрытым collection gate и честным сообщением о недоступности онлайн-заявок. Для публикации работающих форм нужны закрытые технические, договорные и организационные пункты, документированное решение об актуализации записи № `64-22-007585`, юридическое утверждение версии `2026-08-23`, проверка объединённого артефакта и отдельный server approval. Этот репозиторий не отправляет уведомления или изменения сведений в Роскомнадзор и не подтверждает их принятие.
