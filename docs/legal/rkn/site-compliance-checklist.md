## Техническая приёмка объединённой ветки

Эти пункты отмечаются только по объединённому exact-SHA артефакту и production evidence. Часть контрактов покрыта тестами исходников, но это не заменяет проверку фактического сервера.

- [ ] все формы отправляют данные только в собственный same-origin PHP endpoint;
- [ ] production status подтверждает `{"enabled":true}`, а удаление либо неверные права/содержимое `collection-approved` переводят endpoint в fail-closed `enabled:false` без записи;
- [ ] успешный ответ пользователю возвращается только после валидной и устойчивой записи заявки и согласия в SQLite;
- [ ] endpoint валидирует метод, размер, типы, телефон/e-mail, обязательность согласия и ограничивает злоупотребления;
- [ ] `leadId` идемпотентен: повтор запроса не создаёт дубликаты;
- [ ] SQLite, резервные копии, outbox и журналы недоступны из web-root;
- [ ] токены Google/Telegram, пароли и пути к базе отсутствуют в Git, HTML, JS и пользовательских ответах;

## Отдельный gate Google Apps Script → Telegram

Full relay технически восстановлен для существующего Apps Script и закрытой Telegram-группы: после российской записи он формирует плоский payload `_subject`, `_source` и поля формы верхнего уровня. Его исходное состояние — OFF; effective ON требует отдельный `relay-approved` режима `0600`, server flags, точный URL SHA-256 и строгий `{"ok":true}`. Outbox/retry не меняет факт первичной российской записи и не раскрывает секрет браузеру.

Этот fail-closed контур снижает технический риск случайного включения, но не является процедурой ст. 12. Пакет не содержит подтверждения точных иностранных получателей/стран, сведений ч. 5 ст. 12, датированной оценки, подачи отдельного уведомления или статуса его рассмотрения. Перед юридическим выводом нужно установить фактический production state по config/marker/health и журналу outbox; если marker уже включался, зафиксировать период и объём передач.

Для full relay нужны:

- [ ] точные иностранные получатели, юридические лица, адреса и государства;
- [ ] сведения по ч. 5 ст. 12, датированная оценка и отдельное уведомление до начала передачи;
- [ ] истечение применимого срока ожидания для государств вне перечня адекватной защиты и отсутствие запрета/ограничения Роскомнадзора;
- [ ] утверждённые TTL, доступы и проверяемое удаление сообщений;
- [ ] allowlist- и негативные тесты точного плоского payload; серверный допуск `cross_border_confirmed + allow_full + relay-approved`, недоступный из клиента;
- [ ] документированный порядок немедленного выключения relay удалением marker без остановки российского приёма заявок.

Организационно-правовой допуск full mode не считается полученным до одновременного выполнения всех пунктов:

- [ ] требования для full relay выше выполнены;
- [ ] опубликованы обновлённые Политика и отдельное согласие;
- [ ] получено новое согласие пользователей, если оно является основанием передачи;
- [ ] установлены TTL и проверяемое удаление сообщений;
- [ ] проведён технический тест allowlist full mode и отдельный approval владельца.

## Решение по рекламному согласию

Публичная страница рекламного согласия сейчас не нужна. Статья 18 38-ФЗ требует предварительное доказуемое согласие для рекламы по сетям электросвязи, но сайт не заявляет рассылку. Текущий шаблон остаётся внутренним и не добавляется в формы.
