# Пакет подготовки сайта EGOE к требованиям Роскомнадзора

Статус на 27.08.2026: `public-documents-v2026-08-27-ready / collection-active / blockers-open / not-RKN-complete`. Публичные `/privacy/`, `/consent/` и `/cookies/` версии `2026-08-27` в целевом артефакте синхронизированы с активным same-origin приёмом заявок: production принимает их только при одновременной серверной настройке и защищённом `collection-approved`, а полную запись сначала сохраняет в SQLite на REG.RU в РФ. Фактическую публикацию exact-SHA версии нужно подтвердить post-deploy проверкой. Техническое включение не означает, что сведения в реестре Роскомнадзора актуализированы или что организационные обязанности выполнены.

В реестре Роскомнадзора найдена запись Оператора № `64-22-007585`. Наличие записи не снимает необходимость проверить, охватывает ли она новую веб-форму, e-mail, технические поля и SQLite на REG.RU. Результат и границы проверки зафиксированы в [`operator-registry-check.md`](./operator-registry-check.md). Никакое уведомление или изменение сведений из репозитория не направлялось.

## Принцип публикации

Публичные документы должны описывать фактическую работу сайта. Браузер отправляет форму только в same-origin PHP endpoint. Полная заявка и доказательство согласия сначала транзакционно записываются в SQLite вне web-root в РФ; лишь после этого может создаваться задание внешнего relay. До согласованной отправки browser journey не покидает вкладку: в `sessionStorage` сохраняются максимум 20 same-origin страниц текущей вкладки/дня без query/hash, а вместе с заявкой они попадают в существующий `payload_json` и хранятся не дольше лида.

Full Google Apps Script → закрытая Telegram-группа технически реализован как плоский JSON `_subject`, `_source` и поля формы верхнего уровня. Он по умолчанию выключен и эффективен только при отдельном закрытом `relay-approved`, точном SHA-256 разрешённого HTTPS URL, явных mode-specific настройках и строгом ответе `{"ok":true}`. Сбой не отменяет российскую запись: локальный outbox повторяет доставку. Браузер не обращается к Google/Telegram напрямую, а IP/HMAC IP, user-agent и объект согласия во внешний payload не входят. Публичные документы версии `2026-08-27` раскрывают этот последующий маршрут; технический gate не подтверждает его правомерность.

Для безопасного перехода backend временно принимает заявки из уже открытых вкладок с версией согласия `2026-08-23`, но только без browser journey и только в российскую SQLite: такая заявка не создаёт outbox и не может быть отправлена внешним relay даже при его последующем включении. Непустой journey с v23 отклоняется до записи. Во внешний канал допускается только заявка с текущей версией `2026-08-27`; любая иная версия отклоняется.

Российская первичная запись выполняет требование локализации, но не отменяет процедуру трансграничной передачи при последующем доступе Google LLC / Telegram Messenger Inc. Точные иностранные получатели, государства, сведения по ч. 5 ст. 12, датированная оценка, отдельное уведомление и подтверждение его статуса в пакете отсутствуют. Поэтому пакет не имеет статуса RKN-complete, а создание `relay-approved` нельзя трактовать как доказательство завершения процедуры. Фактическое effective-состояние relay перед юридической проверкой устанавливается по production health/config/marker и журналу outbox, а не по тексту репозитория.

Server-only история клиента не меняет schema v2 и не создаёт постоянные идентификаторы: телефон/e-mail нормализуются и сопоставляются по domain-separated HMAC только в памяти при ограниченном чтении retained-заявок. Интерактивной Telegram-кнопки в этой версии нет — для неё отсутствуют исходник Apps Script/токен бота и защищённый webhook. Ежедневная аналитика использует обезличенные агрегаты заявок/КП и опциональный read-only Яндекс Вебмастер; Яндекс Метрика, Envybox и Unisender не используются. FormSubmit отсутствует, Яндекс Карты загружаются автоматически с `loading="lazy"`, WhatsApp открывается только по клику, MAX пока неактивен.

Уведомление Роскомнадзора нельзя заполнять только по сайту, если организация также обрабатывает данные работников, кандидатов, контрагентов, представителей заказчиков или иных лиц. Подготовленный файл содержит готовый сайт-специфичный блок; его нужно объединить с общей картой процессов ООО.

Публичная `/privacy/` также описывает только обработку, связанную с Сайтом. Она не заменяет общую политику и локальные акты Оператора по всем кадровым, договорным, бухгалтерским и иным фактическим процессам.

## Порядок утверждения

1. Подтвердить ответственного за ПД, реальные даты начала процессов, сроки хранения/удаления и полный перечень процессов ООО.
2. Проверить работающий production PHP/SQLite endpoint: российское место базы, права доступа, журнал согласий, journey, резервирование, удаление, инциденты и секреты вне Git; сохранить результаты проверки уже активного сбора.
3. Сверить договорное лицо REG.RU для хостинга и корпоративной почты, место каждой базы и условия поручения. Публичные правила REG.RU не заменяют договор Оператора.
4. Зафиксировать фактическое состояние full relay. До его включения завершить пакет ст. 12; если он уже был включён отдельным marker, не считать marker юридическим подтверждением, сохранить журнал фактических передач и срочно оформить решение с точными получателями/странами, payload, TTL и доступами.
5. Сопоставить запись Роскомнадзора № `64-22-007585` с полной фактической архитектурой сайта и общей картой процессов ООО; письменно решить, требуется ли уведомление об изменении сведений, и сохранить доказательства результата.
6. Проверить отдельные основания на публикацию имени/должности/изображений представителей Оператора по ст. 10.1 152-ФЗ.
7. Провести юридическое утверждение версии `2026-08-27`, UX форм и server-only истории/аналитики в собранном сайте; после deploy подтвердить публичный exact-SHA.
8. Не выдавать наличие страниц, маркеров или зелёных тестов за полное соответствие. Уведомления государству в рамках этого репозитория не отправляются; нужны внешняя подача уполномоченным лицом и сохранённое подтверждение результата.
