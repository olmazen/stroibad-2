# Пакет подготовки сайта EGOE к требованиям Роскомнадзора

Статус на 04.09.2026: `public-documents-v2026-09-04-pre-release / collection-active / direct-telegram-active / corporate-email-copy-prepared / blockers-open / not-RKN-complete`. Целевые `/privacy/`, `/consent/` и `/cookies/` версии `2026-09-04` синхронизированы с same-origin приёмом заявок, прямой серверной доставкой через Telegram Bot API и отдельной автоматической копией на корпоративную почту `zakaz@egoe-life.ru` через локальный Exim и MX REG.RU. Server-only каналы не создают новые cookie и не меняют браузерное хранилище; cookie-документ обновлён только потому, что его прежнее описание Google Apps Script стало фактически неверным. Документы и почтовый код ещё не опубликованы; exact-SHA и effective-состояние каждого канала нужно подтвердить после интеграции и deploy. Техническое включение не означает, что сведения в реестре Роскомнадзора актуализированы или что организационные обязанности выполнены.

В реестре Роскомнадзора найдена запись Оператора № `64-22-007585`. Наличие записи не снимает необходимость проверить, охватывает ли она новую веб-форму, e-mail, технические поля и SQLite на REG.RU. Результат и границы проверки зафиксированы в [`operator-registry-check.md`](./operator-registry-check.md). Никакое уведомление или изменение сведений из репозитория не направлялось.

## Принцип публикации

Публичные документы должны описывать фактическую работу сайта. Браузер отправляет форму только в same-origin PHP endpoint. Полная заявка и доказательство согласия сначала транзакционно записываются в SQLite вне web-root в РФ; лишь после этого создаются разрешённые задания доставки. До добровольной отправки browser journey не покидает вкладку: в `sessionStorage` сохраняются максимум 20 same-origin страниц текущей вкладки/дня без query/hash, а вместе с заявкой они попадают в существующий `payload_json` и хранятся не дольше лида.

Текущий рабочий Telegram-канал вызывает Bot API напрямую с российского сервера и не использует Google Apps Script. В основном `outbox` хранится минимальный payload `schemaVersion/kind/leadId`; непосредственно перед `sendMessage` sender по UUID читает из SQLite только `fields_json`. Сообщение содержит пары полей формы и две служебные кнопки; исходный текст не содержит страницы, referrer, journey, IP/HMAC IP, user-agent или evidence. При нажатии допущенным пользователем кнопки истории bot server-side сопоставляет retained-заявки по телефону/e-mail и может показать ограниченную историю из основной российской базы. Legacy Google Apps Script full relay остаётся в коде для совместимости, но на проверенном production выключен и в текущей доставке заявок не участвует.

Почтовый канал независим от Telegram и включается только одновременно закрытой конфигурацией `shared/leads/config.php` и marker `state/email-delivery-approved` с точным содержимым `egoe-life.ru` и mode `0600`. Отдельный `email_outbox` хранит только `{schemaVersion:1,kind:"email-lead",leadId}`; непосредственно перед отправкой через `/usr/sbin/sendmail`/Exim письмо строится из актуального `fields_json`. Получатель, From и envelope-from фиксированы как `zakaz@egoe-life.ru`, тема фиксирована как `Новая заявка с сайта EGOE`; customer values не попадают в headers, Reply-To отсутствует. Стандартный Date берётся из `received_at`, детерминированный Message-ID — из UUID заявки. В text/html body входят только фиксированный заголовок и все пары полей формы. Journey, page, referrer, IP/HMAC IP, consent evidence, cookie/analytics, вложения, tracking pixels и remote images исключены из body.

Для безопасного перехода backend принимает текущую версию `2026-09-04` и две неизменные legacy-версии. Текущая версия создаёт разрешённые задания прямого Telegram и корпоративной почты. `2026-08-27` нужна для ранее открытых/кэшированных страниц: journey для неё допустим, прямой Telegram сохраняется, но email-задание не создаётся и stale email rows удаляются перед retry. `2026-08-23` допускается только без journey и только в российскую SQLite, без любого внешнего задания. Любая иная версия отклоняется до записи.

Российская первичная запись и корпоративная почта REG.RU не отменяют отдельную процедуру трансграничной передачи при последующем доступе Telegram Messenger Inc. Точные иностранные получатели, государства, сведения по ч. 5 ст. 12, датированная оценка, отдельное уведомление и подтверждение его статуса в пакете отсутствуют. Поэтому пакет не имеет статуса RKN-complete, а создание Telegram marker нельзя трактовать как доказательство завершения процедуры. Фактическое состояние каналов устанавливается по production health/config/markers, таблицам `outbox`/`email_outbox` и подтверждённым сообщениям, а не по исходным defaults или тексту репозитория.

Server-only история клиента не меняет schema v2 и не создаёт постоянные идентификаторы: телефон/e-mail нормализуются и сопоставляются по domain-separated HMAC только в памяти при ограниченном чтении retained-заявок. На production прямой Telegram sender и callback polling были проверены как effective ON, legacy relay — OFF; состояние нужно повторно подтвердить после каждого deploy. Ежедневная аналитика использует обезличенные агрегаты заявок/КП и опциональный read-only Яндекс Вебмастер; Яндекс Метрика, Envybox и Unisender не используются. FormSubmit отсутствует, Яндекс Карты загружаются автоматически с `loading="lazy"`, WhatsApp открывается только по клику, MAX пока неактивен.

Уведомление Роскомнадзора нельзя заполнять только по сайту, если организация также обрабатывает данные работников, кандидатов, контрагентов, представителей заказчиков или иных лиц. Подготовленный файл содержит готовый сайт-специфичный блок; его нужно объединить с общей картой процессов ООО.

Публичная `/privacy/` также описывает только обработку, связанную с Сайтом. Она не заменяет общую политику и локальные акты Оператора по всем кадровым, договорным, бухгалтерским и иным фактическим процессам.

3. Сверить договорное лицо REG.RU для хостинга и корпоративной почты, место каждой базы и условия поручения. Публичные правила REG.RU не заменяют договор Оператора.

Для Telegram завершить пакет ст. 12, не считать marker юридическим подтверждением, сохранить журнал фактических передач и оформить решение с точными получателями/странами, payload, TTL и доступами. Legacy relay оставить выключенным либо отдельно переоценить до любого включения.
5. Сопоставить запись Роскомнадзора № `64-22-007585` с полной фактической архитектурой сайта и общей картой процессов ООО; письменно решить, требуется ли уведомление об изменении сведений, и сохранить доказательства результата.
6. Проверить отдельные основания на публикацию имени/должности/изображений представителей Оператора по ст. 10.1 152-ФЗ.
7. Провести юридическое утверждение `/privacy/`, `/consent/` и `/cookies/` версии `2026-09-04`, UX форм, корпоративной почты и server-only истории/аналитики в собранном сайте; после deploy подтвердить публичный exact-SHA.

9. Не выдавать наличие страниц, маркеров или зелёных тестов за полное соответствие. Уведомления государству в рамках этого репозитория не отправляются; нужны внешняя подача уполномоченным лицом и сохранённое подтверждение результата.
