# План укрепления сайта

Полностью перестроить сайт одним изменением технически возможно, но результат нельзя будет надёжно проверить: релизная система, 300+ страниц, меню, данные, формы и 3D сломаются или пройдут вместе одним непросматриваемым diff. Поэтому работа разделена на законченные пакеты с собственными критериями приёмки.

## P0 — безопасный фундамент

Статус: реализован в ветке `agent/site-foundation`.

- правила будущих сессий;
- allowlist-сборка `dist`;
- release-manifest с SHA-256 каждого файла;
- проверка локальных ссылок, состава и legacy-baseline;
- CI и Pages только из `dist`;
- архивирование опасного старого deploy;
- структура legal/RKN без попадания черновиков в публикацию.

Критерий: все 2 413 публичных source-файлов побайтово совпадают с `dist`, служебных файлов нет, 15 000+ локальных ссылок проверены.

## P1 — единая навигация и каркас страниц

- выбрать шаблонизатор и создать один header/navigation/footer;
- описать навигацию в одном data-файле;
- сначала сгенерировать ограниченную выборку страниц и сравнить DOM/скриншоты;
- затем мигрировать остальные страницы;
- восстановить «Почтовые ящики» во всех нужных меню;
- сохранить «Контейнерные площадки» вне компактного dropdown по согласованному правилу.

Критерий: один источник меню, 303/303 ожидаемых страниц проходят контракт, нет ручных копий общего каркаса.

## P2 — один источник товаров

- определить каноническую схему Product/SKU/URL/price/assets;
- объединить текущие `products.json`, `catalog.json`, `prices.json` и сведения из HTML;
- генерировать search/КП/страницы из одного источника;
- устранить три отсутствующие картинки и расхождения 286/276/268;
- запретить дубли SKU и URL схемой/CI.

Критерий: одна входная коллекция, все производные количества совпадают, каждый URL и ассет существует.

## P3 — runtime и формы

- разделить общий `site.js` на независимые модули;
- локализовать ошибку одной функции, чтобы она не отключала остальной сайт;
- показывать успех формы только после подтверждённого ответа;
- решить и реализовать реальную отправку вложений;
- добавить timeout/fallback для Three.js/Draco/GLB;
- smoke-тесты desktop/mobile критических сценариев.

Критерий: падение внешнего сервиса имеет понятный fallback; формы не сообщают ложный успех; критические сценарии проверяются автоматически.

## P4 — production release

- публичный preview каждого PR;
- обязательный CI и защита `main`;
- production Environment с approval;
- безопасный способ доставки ровно того же artifact на REG.RU;
- post-deploy smoke и проверенный rollback.

Критерий: для любого production-файла известны commit, artifact hash, подтверждение и предыдущая рабочая версия.

## Отдельный поток — документы РКН

Можно выполнять независимо после юридического аудита. Чувствительные исходники остаются в закрытом хранилище, публичные версии добавляются отдельными PR и не смешиваются с миграцией шаблонов или каталога.
