# Правила работы с репозиторием EGOE

Эти правила действуют для всех будущих Codex/Claude-сессий и для любых файлов в репозитории.

## 1. Перед началом работы

1. Выполнить `git status --short --branch`, `git worktree list` и `git rev-parse HEAD`.
2. Не работать поверх чужих незакоммиченных изменений. Если текущий worktree грязный, создать отдельный worktree и ветку от актуального `origin/main`.
3. Одна задача или один чат — одна ветка и один worktree. Не смешивать дизайн, каталог, SEO и инфраструктуру в одном изменении.
4. До правок записать, какие страницы, данные и общие компоненты будут затронуты.
5. Если задача зависит от ещё не слитого PR, создать отдельную ветку поверх его ветки и отдельный stacked PR. Не копировать зависимые изменения вручную и не направлять такой PR сразу в `main`.

## 2. Источник и публикация

- `dist/` — единственный разрешённый артефакт публикации.
- `dist/` генерируется командой `npm run build`, не редактируется вручную и не коммитится.
- Нельзя публиковать корень репозитория, ветку целиком или ZIP без предварительной сборки.
- `dev-*`, `.github/`, `.claude/`, `docs/`, `.private/`, исходники инструментов, редакторы и служебные отчёты не должны попадать в `dist/`.
- Временное исключение: `tools/dogovor/` остаётся публичным legacy-маршрутом, потому что на него ссылаются страницы `/about/` и `/cart/`. Остальной каталог `tools/` не публикуется.
- Production не изменяется без прямого указания пользователя. Сначала проверка ветки и preview/staging, затем отдельное подтверждение production-релиза.
- Один и тот же проверенный артефакт должен переходить между staging и production; пересборка «по дороге» запрещена.

## 3. Изменения сайта

- Единственный источник общей шапки, навигации и подвала — `src/shared/site-shell.json` и renderer `tools/site-shell.mjs`. Блоки между `EGOE:SITE_HEADER` / `EGOE:SITE_FOOTER` в HTML являются сгенерированными и вручную не редактируются.
- После изменения общего каркаса выполнить `npm run sync:shell`; перед передачей результата `npm run check:shell` обязан показать `changedPages: 0`.
- Единственный источник товаров, цен, данных поиска и КП — `src/data/products.json`. `assets/products.json`, `assets/catalog.json` и `assets/data/prices.json` являются сгенерированными: вручную их не редактировать, после изменения источника выполнить `npm run sync:data`.
- Поисковый индекс содержит две разные сущности: все товарные карточки и отдельный список `searchLandings`. Их общее количество намеренно больше числа товаров; проверки должны сравнивать каждый grain отдельно.
- Массовый пересмотр цен применять только через `tools/apply-prices.mjs`: он сначала меняет канонический источник, затем контролируемые поля страниц и производные JSON. Инструменты не должны читать или менять абсолютные пути за пределами репозитория.
- Не делать массовые regex-замены сотен HTML-файлов без отдельного плана миграции, отчёта о масштабе diff и автоматических контрактных проверок.
- Не запускать генераторы, которые удаляют или пересоздают категории, в пользовательском грязном worktree. Сначала временная/чистая ветка, затем проверка diff.
- Не исправлять побочный дефект, если он не входит в задачу: зафиксировать его отдельно.
- Не редактировать сгенерированные файлы, если существует источник или генератор.
- Любое изменение навигации, карточек товаров, canonical/OG, sitemap или общих JS/CSS проверять на всём публичном наборе страниц.
- Каждый новый верхнеуровневый инициализатор в `assets/js/site.js` запускать через именованный `EGOE_RUNTIME.run()` или `value()` с безопасным fallback; имя фиксировать в `config/site-contract.json`. Не возвращать незащищённые top-level IIFE.
- Внешний runtime (Three.js, Draco, GLB и будущие интеграции) обязан иметь ограничение времени и конечное статичное fallback-состояние. Бесконечный loader, ложный success и молчаливое поглощение критической ошибки запрещены.
- После изменения `assets/css/style.css`, `assets/js/site.js`, `assets/js/ad3d.js` или `assets/js/fw3d.js` выполнить `npm run sync:runtime-assets`. Query-версии этих файлов вычисляются из SHA-256 и вручную не подбираются.
- Если изменение затрагивает более 20 HTML-файлов или меняет количество товаров/маршрутов, в отчёте обязательно указать точные количества до и после.

## 4. Данные и приватность

- Не добавлять пароли, токены, FTP-реквизиты, персональные данные, подписи, сканы документов и `.env` в Git.
- Этот репозиторий не является закрытым хранилищем документов. Чувствительные материалы РКН хранятся только в `.private/legal/rkn/` (локально, каталог игнорируется Git) либо во внешнем закрытом хранилище.
- В `docs/legal/rkn/` допустимы только процесс, реестр без персональных данных и публичные/обезличенные шаблоны.
- Документ не попадает на сайт автоматически: для публикации требуется отдельная задача, согласованный публичный текст и явный маршрут.

## 5. Обязательная проверка

Перед передачей результата выполнить:

```bash
npm ci
npm run check
npm run build
```

Дополнительно проверить `git diff --check` и `git status --short`. При изменении интерфейса нужна проверка desktop/mobile затронутых страниц. При изменении ссылок или ассетов проверка должна подтверждать отсутствие битых локальных ссылок в `dist/`.

Проваленную проверку нельзя скрывать. Временное исключение разрешено только как именованный baseline/known debt с точным значением и объяснением; нельзя ослаблять проверку до состояния, в котором она ничего не контролирует.

## 6. Git и релиз

- Не коммитить прямо в `main` и не переписывать историю.
- Не удалять и не сбрасывать чужие изменения командами `reset --hard`, `checkout --`, `clean -fd` или аналогами.
- Перед PR показать осмысленный diff, результаты проверок и состав `dist`.
- Merge — только после зелёного CI. Production — отдельная операция после явного подтверждения.
- В финальном отчёте указать: ветку, исходный commit, изменённые файлы/области, результаты тестов, ссылку на preview (если создан), а также отдельно написать, был ли затронут production.

## 7. Текущий переходный период

HTML-контент страниц пока лежит в корне как legacy-источник, а `tools/build-public-site.mjs` собирает из него безопасный allowlist-артефакт. Общая оболочка и товарные данные уже имеют отдельные канонические источники; CI отклоняет ручной drift производных HTML-регионов и JSON. Верхнеуровневый runtime изолирован guard-слоем, а внешние 3D-загрузки ограничены timeout; следующий пакет — честное подтверждение отправки форм и реальные вложения. Точные счётчики и оставшиеся legacy-исключения фиксируются в `config/site-contract.json`, чтобы новая работа не ухудшала известное состояние незаметно.
